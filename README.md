## Guidance
 
For small, solo-developed games of about four months with a fixed release date and flexible scope, released on Steam.
 
- Populate this document when deciding to turn a prototype into a full project.
- Set the fixed external deadlines first, then work backwards to the due dates.
- When work slips, cut scope, never dates.
- Revise the design and timeline at the vertical slice, once real costs are measured.
- This assumes the Next Fest demo is a time-restricted version of the complete game, finished at the same time.

## Timeline
 
### Milestones
 
| Title | Exit criteria | Due Date |
|---|---|---|
| 0. Prototype | The core mechanic is fun within five minutes and the biggest technical risk is proven. | ____ |
| 1. Design & scope | The design and scope document is published, with its limits and cut rules set. (~5%) | ____ |
| 2. Vertical slice | One section plays at shipping quality and the cost per unit of content is measured. (~15%) | ____ |
| 3. Feature complete | Every planned system works and the game plays from start to finish. (~25%) | ____ |
| 4. Content complete | All content is in and the game can be completed. (~25%) | ____ |
| 5. Release candidate | The final build has no known blockers and is submitted as both the demo and the release build. (~15%) | ____ |
| 6. Launch | The demo has run through Next Fest and the game is live. (~5%) | ____ |
| 7. Hypercare | The launch patch is shipped and no blockers remain open. (~5%) | ____ |
| 8. Review | The post-mortem is written and the decisions for the next project are recorded. (~5%) | ____ |
